# Adopt MCP as the standard for future tool integrations (docs-only)

## Context

The user asked why future tools (weather, Google Maps, Google Calendar)
shouldn't be built as MCP clients / "AI agents" instead of hand-rolled REST
wrappers in `tools.py`, so they "don't mess with the code." Live research
this session confirmed MCP is genuinely more viable now than when the OSM
Maps plan or the currency-tool pattern were originally designed:

- Google shipped an **official, fully-managed remote Calendar MCP server**
  (`calendarmcp.googleapis.com/mcp/v1`, OAuth 2.0, 8 tools) in Developer
  Preview in 2026. ([Google Workspace docs](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server))
- Google also shipped an **official Maps MCP server** ("Maps Grounding
  Lite"), part of the same wave as Calendar, which per Google's
  announcement bundles weather-forecast grounding alongside places/routing
  data. ([Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-official-mcp-support-for-google-services))
- `google-genai`'s Python SDK now has **experimental native MCP support** —
  pass an `mcp.ClientSession` directly into
  `GenerateContentConfig(tools=[...])` and Gemini discovers + calls the
  server's tools automatically, largely replacing the hand-rolled
  `FunctionDeclaration` schema + manual round-trip loop `agent_service.py`
  uses today. ([FastMCP Gemini integration guide](https://gofastmcp.com/integrations/gemini))
- Free, no-API-key **community MCP servers already wrap Open-Meteo**
  (e.g. `cmer81/open-meteo-mcp`, `JeremyMorgan/Weather-MCP-Server`,
  `gbrigandi/mcp-server-openmeteo`) — the exact source CLAUDE.md's decision
  log already earmarked for a weather re-add.

One important correction to the framing: MCP does **not** mean tools "talk
to the LLM directly" and bypass the backend's code. The FastAPI backend
remains the MCP *client* — it still owns the connection to each MCP server
(remote HTTP or a self-hosted subprocess), still routes results through
Gemini, and still needs the same anti-fabrication grounding (principle #7)
regardless of transport. What MCP genuinely buys is *less hand-written
REST-wrapper code* and a standard shape, not a change in who's in the loop.

Per the user's answers to clarifying questions asked before this plan:
- **Scope**: architecture decision only, recorded in `CLAUDE.md`. No code
  changes today — Maps/Calendar get built as MCP clients when their actual
  build-order turn comes.
- **Maps**: switch to Google's official Maps MCP server, knowingly
  reopening and reversing the OSM-stack decision (accepting the Google
  Cloud billing-account requirement that decision was originally made to
  avoid).
- **Weather**: evaluate *both* a self-hosted community Open-Meteo MCP
  server *and* building a small lightweight one ourselves — not decided
  now, recorded as an open evaluation for when weather is actually rebuilt.

This plan is a single, careful edit to `CLAUDE.md` — the project's source
of truth for these decisions — updating the architecture principles and
decision log to reflect the above, without touching any application code
(nothing in `backend/` or `frontend/` changes).

### 1. New architecture principle (append after existing #7)

Add as principle **#8**, matching the file's existing voice/density:

> 8. **Prefer MCP for new external tool integrations, when a trustworthy
>    server exists.** As of Aug 2026, Google ships fully-managed, officially
>    supported remote MCP servers for both Calendar (`calendarmcp.
>    googleapis.com`) and Maps (via Google Maps Platform), and `google-genai`'s
>    Python SDK has experimental native MCP support — pass an
>    `mcp.ClientSession` straight into `GenerateContentConfig(tools=[...])`
>    and Gemini both discovers the server's tools and calls them, largely
>    replacing the hand-rolled `FunctionDeclaration` schema + manual
>    round-trip loop that `agent_service.py`/`tools.py` use today for
>    currency. This does **not** mean tools "talk to the LLM directly"
>    bypassing the backend — the backend is still the MCP *client*: it still
>    owns the connection to each MCP server (remote HTTP or a self-hosted
>    subprocess), still routes results through Gemini, and still needs the
>    same anti-fabrication grounding (principle #7) regardless of transport.
>    What MCP actually buys: less hand-written REST-wrapper code, and a
>    standard shape that scales to more integrations without every one
>    becoming a bespoke client. Decide per integration, not blanket:
>    - An **official, managed, remote** MCP server (HTTP/OAuth, e.g.
>      Calendar's) is the easy case — no subprocess to run, no third-party
>      code to vet, roughly interchangeable with hand-rolling the same calls
>      via `googleapiclient`.
>    - A **self-hosted third-party** MCP server (stdio subprocess/container,
>      e.g. a community Open-Meteo weather server) trades hand-written REST
>      code for a Docker Compose service and a third-party codebase you now
>      have to trust and keep updated — evaluate it like any new dependency,
>      don't add one uncritically just because it exists.
>    - A **small MCP server we write ourselves** is often better than
>      importing a third-party one when the tool surface is narrow — one
>      purpose-built tool with the exact flat/pre-aggregated shape
>      principle #2 already requires, versus a generic multi-tool community
>      server with more surface area (and more to trust) than the app needs.
>    - `google-genai`'s MCP support is **experimental** — re-verify it's
>      graduated (or learn its current limitations) before depending on it
>      for anything load-bearing, same as every other dated fact in this
>      file.
