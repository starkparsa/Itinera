# Itinera

A chat-driven trip planner: describe a trip in plain language, get a
day-by-day itinerary generated by Gemini, refine it conversationally,
export it to Google Calendar.

**Project docs, four files:**
- **This file** — what it is, how to run it, useful links.
- [`STATUS.md`](STATUS.md) — where things stand right now, what's live vs.
  paused, the next action, known blockers. **Read this first if you're
  picking the project back up.**
- [`decisions.md`](decisions.md) — what was decided, why, and when to
  revisit each decision.
- [`progress.md`](progress.md) — dated diary of what happened each session.

Plus `docs/architecture.md` (system diagrams), `docs/deployment-guide.md`

## Stack

- **Frontend**: Next.js (App Router, TypeScript), Tailwind v4 + shadcn/ui.
- **Backend**: FastAPI + SQLAlchemy.
- **Database**: Postgres, hosted on [Neon](https://neon.tech) (free tier,
  no card) — local dev and prod point at the same kind of managed
  instance, no local DB server to run.
- **LLM**: Gemini API (`google-genai`) — `gemini-3.5-flash-lite` by
  default, free tier, no card required. Falls back automatically to Groq
  (also free, no card) if Gemini's request quota is exhausted.
- **CI/CD**: GitHub Actions — lint + test on every push/PR, build & push
  Docker images to GHCR on merges to `main`.

See `decisions.md` for the rationale behind each of these.

## Prerequisites

- Docker Desktop
- A free `GEMINI_API_KEY` from [Google AI Studio](https://aistudio.google.com/apikey)
  (no card needed)
- Optional but recommended: a free `GROQ_API_KEY` from
  [console.groq.com/keys](https://console.groq.com/keys) (no card needed) —
  enables the automatic fallback above. Without it, a Gemini quota failure
  just raises the usual error.
- To actually log in (Google OAuth): a Google Cloud project with an OAuth
  client ID (Web application) — console.cloud.google.com → APIs & Services
  → Credentials. Authorized redirect URI:
  `http://localhost:3000/api/auth/callback/google`. Without this the app
  still runs and builds fine, but every login attempt fails at Google's
  own consent screen (`invalid_client`).
- To push an itinerary to Google Calendar: the **Google Calendar API**
  enabled on that same Cloud project (APIs & Services → Library → Google
  Calendar API → Enable) — a real OAuth client alone isn't enough. Also
  needs a `TOKEN_ENCRYPTION_KEY` in `.env` (generate with
  `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`).
  Without either, everything else works fine — only "Push to Google
  Calendar" fails.
- Optional, billed: `GOOGLE_PLACES_API_KEY` for richer place details and
  nearby-place recommendations. Leave blank for Wikipedia-only place
  context.

## Running the app, step by step

### 1. Set up environment variables

```bash
cp .env.example .env
```

Fill in at minimum `GEMINI_API_KEY`. Everything else has a usable
default, **except real login**: without a real `AUTH_GOOGLE_ID`/
`AUTH_GOOGLE_SECRET`/`AUTH_SECRET`/`AUTH_BACKEND_SECRET`, the app still
builds and runs, but every sign-in attempt fails at Google's own consent
screen. If running the frontend with `npm run dev` (the non-Docker path
below) rather than through `docker compose`, also copy its own env file,
since that path reads from here instead of the root `.env`:

```bash
cp frontend/.env.local.example frontend/.env.local
```

`AUTH_BACKEND_SECRET` must be the **exact same value** in both files, or
every backend call 401s.

### 2. Start it — pick one path

**Option A — Docker Compose (recommended, one command):**

```bash
docker compose up --build
```

- Frontend: http://localhost:3000
- Backend API docs: http://localhost:8000/docs
- Database: whatever `DATABASE_URL` in your root `.env` points at (Neon
  Postgres) — `docker-compose.yml` passes it straight through, there's no
  local DB container in the default path. A local MySQL service still
  exists behind the `legacy-mysql` Compose profile if specifically needed;
  nothing reads from it by default.

If this hangs or a `docker ps`/`docker compose` command itself fails to
reach the Docker daemon, Docker Desktop is most likely stuck mid-startup —
restart the app and retry before assuming it's a project issue.

**Option B — without Docker (two terminals, faster iteration):**

Terminal 1 — backend:

```bash
cd backend
python -m venv .venv && source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Reads `DATABASE_URL` from `.env`; fails fast with a clear error if unset,
rather than silently defaulting to a local database that may not exist.
For a quick run with no external dependency at all:

```bash
DATABASE_URL="sqlite:///./dev.db" uvicorn app.main:app --reload
# Windows (PowerShell): $env:DATABASE_URL="sqlite:///./dev.db"; uvicorn app.main:app --reload
```

Terminal 2 — frontend:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:3000.

### 3. Verify it's up

- http://localhost:8000/docs loads the backend's interactive API docs.
- http://localhost:3000 redirects to `/login` if you're not signed in yet
  — that's expected.

### 4. Sign in and try it

Sign in with Google (needs the real OAuth client from step 1), then type
a trip request in the chat, e.g. **"plan a 5 day trip to Lisbon."**

## Running tests

```bash
cd backend
pip install -r requirements.txt -r requirements-dev.txt
pytest -v
```

Tests use an in-memory SQLite database and mock the Gemini calls, so no
live Postgres instance or `GEMINI_API_KEY` is needed to run them.

## Database migrations

`main.py` still calls `Base.metadata.create_all()` on startup — harmless
against a DB that already has all its tables, and what makes a fresh
SQLite/Postgres instance work with zero setup. Alembic (`backend/alembic/`)
is what actually changes an *existing* table's schema:

```bash
cd backend
alembic upgrade head        # apply pending migrations
alembic stamp head          # mark as applied without running, for a DB
                             # create_all() already built from scratch
alembic revision --autogenerate -m "description"   # after changing models.py
```

**Before running `--autogenerate` or `upgrade head` against a real
database, read the generated migration file** — see `progress.md`'s
2026-08-26 entries for why this matters concretely, not just in theory.

## Troubleshooting

**"502 Server Error: Bad Gateway" from `/trips/generate`** — the backend
reached out to Gemini (and, if `GROQ_API_KEY` is set, the Groq fallback
too) and both failed. Most often this means `GEMINI_API_KEY` is
missing/invalid, the free-tier request quota was exhausted with no
`GROQ_API_KEY` configured to fall back to, or `GEMINI_MODEL` doesn't
exist (Google retires model strings without much notice — check
`ai.google.dev/gemini-api/docs/models` if it 404s). Check the backend
logs for `RESOURCE_EXHAUSTED` specifically — that's a quota problem, not
a code/deploy one. The error response's `detail` field states the
specific cause.
