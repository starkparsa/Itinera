# AI Travel Planner

A chat-driven trip planner: describe a trip in plain language, get a day-by-day
itinerary generated by Gemini, stored in Postgres (Neon).

## Stack
- **Frontend**: Next.js (App Router, TypeScript) chat UI. Migrated off
  Streamlit — see CLAUDE.md's decision log for why (Streamlit can't host an
  OAuth callback route or read browser cookies, both needed for the planned
  Google login). No auth yet as of this migration (Phase A of that plan);
  every request still runs under a placeholder user, same as before.
- **Backend**: FastAPI + SQLAlchemy
- **Database**: Postgres, hosted on [Neon](https://neon.tech) (free tier, no
  card) — both local dev and prod point at the same kind of managed instance,
  no local DB server to run. (Migrated off local MySQL 2026-08-29; see
  CLAUDE.md's decision log.)
- **LLM**: Gemini API (`google-genai`) — `gemini-3.5-flash-lite` by default,
  free tier, no card required. Falls back automatically to Groq (also free,
  no card) if Gemini's request quota is exhausted — see CLAUDE.md's decision
  log for why.
- **CI/CD**: GitHub Actions — lint + test on every push/PR, build & push Docker
  images to GitHub Container Registry on merges to `main`

## Prerequisites
- Docker Desktop
- A free `GEMINI_API_KEY` from [Google AI Studio](https://aistudio.google.com/apikey)
  (no card needed)
- Optional but recommended: a free `GROQ_API_KEY` from
  [console.groq.com/keys](https://console.groq.com/keys) (no card needed) —
  enables the automatic fallback above. Without it, a Gemini quota failure
  just raises the usual error.
- To actually log in (Google OAuth): a Google Cloud project with an OAuth
  client ID (Web application) -- console.cloud.google.com -> APIs & Services
  -> Credentials. Authorized redirect URI: `http://localhost:3000/api/auth/callback/google`.
  Without this the app still runs and builds fine, but every login attempt
  fails at Google's own consent screen (`invalid_client`) -- see CLAUDE.md's
  decision log, "Auth" row.
- To push an itinerary to Google Calendar: the **Google Calendar API**
  enabled on that same Cloud project (APIs & Services -> Library -> Google
  Calendar API -> Enable) -- a real OAuth client alone isn't enough, calls
  fail with "Calendar API has not been used in this project" until it's
  turned on. Also needs a `TOKEN_ENCRYPTION_KEY` in `.env` (generate with
  `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`).
  Without either, everything else works fine -- only the "Push to Google
  Calendar" button fails.

## Running the app, step by step

### 1. Set up environment variables
```bash
cp .env.example .env
```
Fill in at minimum `GEMINI_API_KEY` (free, no card — see Prerequisites).
Everything else has a usable default, **except real login**: without a real
`AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`/`AUTH_SECRET`/`AUTH_BACKEND_SECRET`
(see Prerequisites), the app still builds and runs, but every sign-in
attempt fails at Google's own consent screen — you won't be able to get
past the login page to actually chat. If you're running the frontend with
`npm run dev` (the non-Docker path below) rather than through
`docker compose`, also copy its own env file, since that path reads from
here instead of the root `.env`:
```bash
cp frontend/.env.local.example frontend/.env.local
```
`AUTH_BACKEND_SECRET` must be the **exact same value** in both files, or
every backend call 401s.

### 2. Start it — pick one path

**Option A — Docker Compose (recommended, one command):**
```bash
docker compose up --build
```
- Frontend: http://localhost:3000
- Backend API docs: http://localhost:8000/docs
- Database: whatever `DATABASE_URL` in your root `.env` points at (Neon
  Postgres — see Prerequisites) — `docker-compose.yml` passes it straight
  through, there's no local DB container in the default path anymore. A
  local MySQL service definition still exists in `docker-compose.yml`
  behind the `legacy-mysql` profile (`docker compose --profile legacy-mysql
  up mysql`) if you specifically need it for something; nothing reads from
  it by default.

If this hangs or a `docker ps`/`docker compose` command itself fails to
reach the Docker daemon, Docker Desktop is most likely stuck mid-startup
(confirmed live: it can sit in a state where even a basic engine ping
returns `500`) — restart the Docker Desktop app and retry before assuming
it's a project issue.

**Option B — without Docker (two terminals, faster iteration while developing):**

Terminal 1 — backend:
```bash
cd backend
python -m venv .venv && source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```
Reads `DATABASE_URL` from `.env` (Neon Postgres — see Prerequisites); the
app now fails fast with a clear error if it's unset, rather than silently
defaulting to a local database that may not exist. For a quick run with no
external dependency at all, override to a local SQLite file instead:
```bash
DATABASE_URL="sqlite:///./dev.db" uvicorn app.main:app --reload
# Windows (PowerShell): $env:DATABASE_URL="sqlite:///./dev.db"; uvicorn app.main:app --reload
```

Terminal 2 — frontend:
```bash
cd frontend
npm install
npm run dev
```
Open http://localhost:3000.

### 3. Verify it's up
- http://localhost:8000/docs loads the backend's interactive API docs.
- http://localhost:3000 redirects to `/login` if you're not signed in yet —
  that's expected, not a bug.

### 4. Sign in and try it
Sign in with Google (needs the real OAuth client from step 1), then type a
trip request in the chat, e.g. **"plan a 5 day trip to Lisbon"**.

## Running tests
```bash
cd backend
pip install -r requirements.txt -r requirements-dev.txt
pytest -v
```
Tests use an in-memory SQLite database and mock the Gemini calls, so no
live Postgres instance or `GEMINI_API_KEY` is needed to run them.

## Database migrations
`main.py` still calls `Base.metadata.create_all()` on startup -- harmless
against a DB that already has all its tables, and what makes a fresh
SQLite/Postgres instance work with zero setup. Alembic (`backend/alembic/`) is
what actually changes an *existing* table's schema now (added alongside the
Google OAuth work, see CLAUDE.md's decision log):
```bash
cd backend
alembic upgrade head        # apply pending migrations
alembic stamp head          # mark as applied without running, for a DB
                             # create_all() already built from scratch
alembic revision --autogenerate -m "description"   # after changing models.py
```

## Intent routing, scope restriction, and latency
Every message used to be forced through full itinerary generation, even
plain questions -- which produced nonsensical fake itineraries in response
to things like "what's the weather like there?". This is now fixed with a
classification step (`classify_intent` in `llm_service.py`) that runs
**before** anything expensive, sorting each message into:
- **`new_trip` / `edit_trip`** -- runs the full chunked itinerary pipeline,
  same as before. Note: `edit_trip` currently still regenerates the whole
  itinerary (with conversation context describing the requested change)
  rather than surgically editing specific days -- true diff-based editing
  is a bigger feature for later. A prompt with no day-count language (e.g.
  "I want to experience the artsy side of it" after a 5-day trip was
  already generated) preserves the previously-established trip length as a
  soft default rather than re-guessing it from scratch -- it's still fully
  changeable by saying so ("make it a full week instead").
- **`question`** -- answered conversationally via real chat-formatted
  history (not the squashed summary string), without touching the
  itinerary generator at all.
- **`off_topic`** -- returns a fixed, non-LLM-generated decline message
  immediately. This is also the scope guardrail: off-topic requests
  (coding help, general trivia, prompt-injection attempts) never reach the
  agent or itinerary machinery, and the decline text itself can't be
  manipulated since it's not model-generated.

The same classification call also detects when a message explicitly asks
the assistant to act as a **tour guide** (e.g. "be my tour guide", "take me
through this place") -- see "Tour-guide mode" below for what that turns on.

This closes the latency gap for anything that isn't a genuine trip request
(no agent loop, no chunked generation for a question or a decline), and the
assistant's stored summaries after a trip is generated now include real
day/activity detail (see `_summarize_itinerary` in `routers/trips.py`)
instead of a one-line "planned a trip to X" -- so follow-up turns actually
have something concrete to reference.

**For itinerary generation itself**, two further latency notes:
- Every Gemini call sets `thinking_config` to `MINIMAL` — `gemini-3.6-flash`
  (used until 2026-08-25, see CLAUDE.md's decision log for why it was
  swapped out) was a reasoning model that otherwise spends part of its
  output-token budget on invisible "thinking" tokens before the visible
  answer; `MINIMAL` keeps classification/extraction/generation fast and
  cheap, and is confirmed harmless on the current `gemini-3.5-flash-lite`
  too even though it isn't a reasoning model in the same sense.
- The agentic tool-calling step and the destination/day-count inference
  call are independent, so they now run concurrently rather than
  back-to-back, removing roughly one full model round-trip's worth of wait
  time from every generation.

## Chat history and conversation memory
The app now works like a real chat interface rather than one-shot trip
generation:
- **Sidebar chat history** — every trip request starts or continues a
  conversation, listed in the sidebar with a "New chat" button to start
  fresh (mirrors the `conversations` + `messages` tables in `models.py`).
- **Conversation memory** — when you continue a chat (e.g. "actually make it
  a full week" or "make it vegetarian friendly"), the backend builds a short
  summary of recent turns (`_build_conversation_context` in
  `routers/trips.py`) and folds it into every LLM prompt, so follow-ups can
  reference what was discussed earlier in that chat. This is a best-effort
  summary, not full raw history — it's capped (`MAX_CONTEXT_MESSAGES`,
  `MAX_CONTEXT_CHARS`) to keep prompts bounded regardless of how long a
  conversation gets.
- Switching chats in the sidebar reloads that conversation's full message
  history, including past itineraries, from the database.

## Weather

Real per-day forecasts (Open-Meteo, free, no key) are fetched directly for
every trip with a resolved `start_date` -- **not** through the agentic
tool-calling loop below at all. "Does this trip get a forecast" is never a
judgment call the model makes, so `weather_service.py` is called straight
from the routers on every trip/reload instead, at zero extra LLM cost.
Shown in the UI per day, and folded into Q&A answers on every question turn
so a follow-up like "what should I pack?" is grounded in the real numbers
instead of an invented one. Cached per-trip with a 3-hour TTL.

## Agentic tool-calling

Two **separate** tool-calling loops in `agent_service.py`, each with its
own on/off flag and its own tool schema -- deliberately not one shared
loop, since they have different caching needs (see below):

- **Currency conversion** (`tools.py`, via Frankfurter/ECB rates) —
  **currently paused** (`agent_service.AGENT_TOOL_CALLING_ENABLED = False`,
  a product decision, not a reliability problem — the tool/schema are still
  in place). Runs once per conversation, up front, before itinerary
  generation; its finding is cached on `Conversation.agent_context` and
  reused on every later edit turn rather than re-running.
- **Place context** (`tools.py`'s `get_place_context`, via Wikipedia — free,
  no key) — **on by default**
  (`agent_service.QA_TOOL_CALLING_ENABLED = True`). Reachable only from
  conversational `question`-intent turns, and run **fresh on every such
  turn** (never cached across turns, unlike currency) since a different
  place can be asked about each time. Defaults to a brief 1-3 sentence
  overview; only gives a fuller, multi-paragraph answer when the user's own
  words ask for more (e.g. "give me the full history", "be my tour guide").

While a loop is paused, its function returns `""` immediately with no
network call, so generation/Q&A behaves exactly as if nothing useful was
found. Both are best-effort: if a tool API is unreachable, the turn
proceeds normally without it rather than failing.

**Note:** Gemini's native function calling (`response.function_calls`,
`types.FunctionDeclaration`) replaced the old hand-rolled Ollama tool loop.
Function calling reliability is a known, documented caveat for Gemini too
(not unique to local models), particularly in long conversations under the
default `function_calling_config.mode="AUTO"` — worth keeping in mind if a
paused loop gets re-enabled and starts behaving oddly.

## Tour-guide mode

Once you explicitly ask the assistant to act as a tour guide ("be my tour
guide", "take me through this place"), later follow-up questions in the
same conversation keep getting that fuller, narrative-guide style by
default too — even ones that don't repeat the phrasing — until you
explicitly go back to planning/editing the itinerary (at which point it
turns back off). This is real, persisted state
(`Conversation.tour_guide_mode`), not just a per-message model judgment:
the same `classify_intent` call that already routes each message also
detects the trigger phrase, at no extra LLM cost.

## Troubleshooting

**"502 Server Error: Bad Gateway" from `/trips/generate`** — the backend
reached out to Gemini (and, if `GROQ_API_KEY` is set, the Groq fallback too)
and both failed, so it returns a 502 rather than a broken itinerary. Most
often this means `GEMINI_API_KEY` is missing/invalid, the free-tier request
quota was exhausted with no `GROQ_API_KEY` configured to fall back to, or
`GEMINI_MODEL` doesn't exist (currently `gemini-3.5-flash-lite` -- Google
retires model strings without much notice, so this is worth checking first
if it 404s: `ai.google.dev/gemini-api/docs/models`). Check the backend
container logs for `RESOURCE_EXHAUSTED` specifically -- that's a quota
problem, not a code/deploy one; see CLAUDE.md's decision log.
The `detail` field in the error response states the specific cause
(missing key, rate limit, invalid model, etc.) so you don't need to guess.

## How long trips are generated
Trips longer than a few days are generated in chunks (5 days per LLM call by
default) rather than one giant response — native structured output
guarantees the *shape* of what comes back is valid JSON, but not that
content quality/variety holds up over a very long single generation, and
chunking also drives an anti-repetition mechanism (`covered_activities`)
that's unrelated to output-shape validity and would need to stay regardless.
This keeps each individual request small regardless of total trip length.
Trip length
is inferred by the model from the prompt itself (e.g. "a week in Lisbon" ->
7 days) -- say how long the trip is in your message rather than a separate
field. The API's `/trips/generate` endpoint also accepts an explicit `days`
override for programmatic callers, but the frontend doesn't expose it.
Requests are capped at
`MAX_TOTAL_DAYS` (60, configurable in `llm_service.py`) to avoid unbounded
generation time; longer requests are silently clamped and a note is returned
explaining the cap.

Expect multi-week trips to take a few minutes, since each chunk is a
separate sequential call to the model.
