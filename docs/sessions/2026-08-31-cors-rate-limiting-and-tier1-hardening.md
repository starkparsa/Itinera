# 2026-08-31 — CORS/rate-limiting fix, then Tier 1 scale hardening

**A full architecture review (prompted by the user explicitly reframing
this as a real product, not a hobby project) produced a prioritized list of
findings; this session shipped the two highest-priority ("Tier 0") items
plus every "Tier 1" item that didn't require a product decision.**

## Changes shipped

- **CORS**: `backend/app/main.py`'s `allow_origins=["*"]` replaced with an
  explicit `ALLOWED_ORIGINS` env-var allow-list (defaults to the local
  Next.js dev origin); `allow_methods`/`allow_headers` narrowed from `["*"]`
  to what the API actually uses.
- **Rate limiting**: new `backend/app/rate_limit.py` (slowapi, IP-keyed) —
  a 100/minute app-wide default plus a stricter 10/minute cap specifically
  on `POST /trips/generate` (the one route that always makes a real
  Gemini/Groq call). In-process/in-memory; not shared across replicas if
  the backend is ever horizontally scaled, see that file's docstring.
- **DB indexes**: `index=True` added to every foreign-key column in
  `models.py` (`Conversation.user_id`, `Trip.user_id`/`conversation_id`,
  `Message.conversation_id`, `ItineraryItem.trip_id`) — Postgres never
  auto-indexes these the way it does a primary key, so every ownership
  check and every conversation/trip lookup was an unindexed scan. Migration
  `98900a8d691c`, applied live to Neon and verified via
  `information_schema`.
- **`get_conversation` N+1 + redundant weather refresh**: new
  `weather_service.read_cached_weather()` (cache-only, no network) plus
  `selectinload`-based eager loading of `messages -> trip -> items`.
  `get_conversation` now only runs the real freshness-checking
  `get_or_refresh_trip_weather` for a conversation's *latest* trip; every
  older trip (one per past edit turn) is served from cache. Previously
  every trip-bearing message got the full freshness-check-plus-possible-
  live-fetch treatment on every single reload, scaling with edit count for
  no real benefit.
- **`list_conversations` pagination**: `limit`/`offset` query params,
  default 100, hard-capped at 200 (FastAPI itself 422s above that, not a
  silent clamp). No frontend change needed yet — current usage is well
  under the default.
- **Per-account daily quota**: new `backend/app/usage_quota.py` +
  `User.daily_request_count`/`daily_request_count_date` (migration
  `4e14c7bab841`, applied live to Neon). A flat `DAILY_TRIP_GENERATION_LIMIT`
  (default 20/day) checked and consumed at the very top of `generate_trip`,
  before `classify_intent` or any other LLM work — a real per-account cost
  ceiling, distinct from `rate_limit.py`'s IP-based flood protection (DB-
  backed specifically so it holds even if the backend is ever scaled to
  multiple instances).

## Bugs found & fixed

- The quota-columns migration's autogenerated `daily_request_count` column
  was `nullable=False` with no `server_default` — would have failed against
  the `users` table's existing rows. Same class of incident CLAUDE.md
  already documents for the `tour_guide_mode` migration; caught the same
  way (reading the generated file before applying it), fixed with
  `server_default=sa.text('0')`.
- A new test (`test_conversation_reload_only_refreshes_weather_for_the_
  latest_trip`) initially asserted on `call_args.args[0].id` *after* the
  request completed — raised a real `DetachedInstanceError`, since
  `get_conversation`'s own `db.commit()` expires ORM object attributes by
  default and the request's session is closed by the time `client.get()`
  returns. Fixed by capturing trip ids via `side_effect` while the session
  was still open, not by reading `call_args` back afterward.

## Key learnings

- slowapi's `@limiter.limit(...)` decorator requires a parameter *literally
  named* `request` (it inspects the function signature by name, not type) —
  `routers/trips.py`'s `generate_trip` had to rename its existing
  `request: schemas.TripRequest` body param to `trip_request` to make room
  for the real `request: Request` slowapi needs.
- `SlowAPIMiddleware` applies `Limiter(default_limits=...)` to every route
  automatically via ASGI route-matching — no `request:` param needed on
  routes that only want the default limit. Only a route with its own
  stricter `@limiter.limit(...)` decorator needs one.
- A stray live smoke test (manually curl-ing the real running server with a
  valid signed token, no LLM mocking, to sanity-check the rate limiter)
  cost one real `GEMINI_API_KEY` call before it was caught and the server
  killed — worth remembering: prefer `TestClient` + mocks, or an invalid
  token, for anything beyond a pure-CORS/pure-429-threshold smoke check.
- Autogenerated Alembic migrations were run twice this session directly
  against the live Neon database (introspection for `--autogenerate`,
  then `upgrade head` after review) — both were additive/reversible and
  applied cleanly with no measurable lock time at current table sizes (low
  hundreds of rows per table).

## Open items / follow-ups

- Tier 0 items *not* done this session: real observability/error tracking,
  confirming the Groq fallback actually works under load, budgeting a paid
  Gemini tier, confirming Neon's backup/PITR posture, moving secrets out of
  plaintext `.env` for the real deploy target.
- `rate_limit.py`'s in-memory storage and `usage_quota.py`'s flat
  per-account number both explicitly assume today's single-instance,
  no-pricing-tiers stage — revisit both once the backend is horizontally
  scaled or a real plan/pricing model exists.
- No frontend "load more" UI for `list_conversations`'s new pagination —
  not needed yet at current usage, backend just won't scale unbounded
  anymore.
