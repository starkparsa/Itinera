# 2026-08-27 — Persistent tour-guide mode

**Once the user explicitly asks the assistant to be a tour guide, the
conversation now stays in that fuller, narrative-guide style for later
Q&A follow-ups too — even ones that don't repeat the phrasing — until the
user explicitly goes back to itinerary planning/editing.**

## Changes shipped

- `backend/app/llm_service.py`: `IntentResult` gained a second field,
  `tour_guide_requested: bool = False`, extracted by the SAME `classify_intent`
  Gemini call that already decides `new_trip`/`edit_trip`/`question`/
  `off_topic` — no extra network round-trip. `INTENT_INSTRUCTIONS` gained a
  paragraph explaining the field reports only what *this* message asked
  for, not what mode the conversation is already in, and that it can only
  be `true` when `intent == "question"`. `classify_intent`'s return type
  changed from `str` to `tuple[str, bool]` (matching `_infer_trip_meta`'s
  existing `tuple[str, int]` convention in the same file).
- `backend/app/models.py`: new `Conversation.tour_guide_mode` column
  (`Boolean, nullable=False, default=False`), persisted state that
  survives across turns/reloads. Alembic migration `65524d890048` (chained
  after `f0fa120ecdf7`) — hand-added `server_default=sa.false()` since the
  autogenerated file only had the Python-side ORM default, which would
  have failed against a real table with existing rows (per this project's
  documented past incident, the generated file was read before applying,
  not trusted blindly).
- `backend/app/agent_service.py`: `answer_question_with_tools` gained a
  `tour_guide_mode: bool = False` parameter — folds a persistent-mode note
  into the system prompt (distinct from `QA_TOOL_SYSTEM_PROMPT`'s existing
  per-turn "be my tour guide" → `detail="detailed"` instruction, which only
  covers the triggering turn's own wording) explicitly telling the model to
  keep calling `get_place_context` with `detail="detailed"` and giving
  fuller answers on later turns too. Return type unchanged (`str`) —
  mode-on/off detection lives entirely on the input side.
- `backend/app/routers/trips.py`: the `question` branch reads
  `conversation.tour_guide_mode` (as it stood *entering* the turn) into
  `answer_question_with_tools`, then sets it `True` if this turn's
  `tour_guide_requested` came back true. The `new_trip`/`edit_trip` branch
  unconditionally sets it `False` — "off" always wins on a planning turn,
  regardless of what `tour_guide_requested` said, so there's no ambiguous
  state even if the model doesn't perfectly obey the "can't coincide with
  edit_trip/new_trip" instruction.
- Mechanical, wide-blast-radius test update: every mock of
  `classify_intent` across the whole `backend/tests/` tree (28 call sites
  across `test_trips_router.py`, `test_calendar_push_router.py`,
  `test_calendar_export.py`, `test_ownership_isolation.py`) updated from a
  bare string return to a 2-tuple. 8 new tests. Full suite: 215 passed.

## Key learnings

- **Grep the return-type blast radius across the WHOLE test tree, not just
  the files a design pass names.** The design plan for this feature
  identified `test_trips_router.py` (19 mock sites) as needing updates for
  `classify_intent`'s new tuple return, but a direct `grep -r
  classify_intent backend/tests/` before starting found 3 more files
  (`test_calendar_push_router.py`, `test_calendar_export.py`,
  `test_ownership_isolation.py` — 9 more sites) that also mock it and would
  have failed silently if not caught before implementation started.
- The live-verification step surfaced one thing worth naming even though
  it turned out not to be a bug: a "vague follow-up with no tour-guide
  language" reply looked notably shorter on the first live sample (~260
  chars, 2 sentences) than expected for "fuller, narrative style." Repeating
  the same turn 1→turn 2 sequence twice more (fresh conversations) showed
  natural variance (260–711 chars) — all samples correctly listed real,
  grounded neighboring places with no fabricated venue names, just varying
  in how expansive the model chose to be turn to turn. Confirmed via a
  direct instrumented trace that the persistent-mode note IS present in
  the system prompt on these turns — the wiring itself is correct; LLM
  output length for an open-ended "what else is nearby" question is
  inherently variable, not a sign the feature isn't working.
- Live-verified the adversarial case (a message combining tour-guide
  phrasing with an explicit replan request, "be my tour guide through a
  new 3-day Rome itinerary"): the model classified it as a planning turn
  (a real itinerary was generated) and `tour_guide_mode` correctly stayed
  `False` — the router's unconditional "off wins" ordering worked exactly
  as designed regardless of what the model's `tour_guide_requested` field
  did internally.

## Live verification (all scenarios passed)

One continuous conversation, real Gemini calls, Little Haiti (reusing this
session's already-verified grounding):

1. `"i think i am already in little haiti can you be my tour guide and
   take me through this place"` → detailed narrative reply, correctly
   grounded (Toussaint L'Ouverture statue, "Lemon City"), no fabricated
   venues. `conversation.tour_guide_mode` confirmed `1`/True in the DB
   immediately after.
2. `"what else is nearby?"` (no tour-guide language) → still a fuller,
   grounded reply about neighboring Miami areas (Wynwood, Design District,
   MiMo District, etc.), repeated 3 times for consistency — all correctly
   avoided inventing specific venues.
3. `"actually let's plan a proper 3-day itinerary"` → a real itinerary
   regenerated (trip_id assigned, 22 items), `conversation.tour_guide_mode`
   confirmed flipped back to `0`/False in the DB.
4. `"tell me about the Toussaint statue"` (plain follow-up after the
   planning turn) → back to a brief, 2-sentence default reply (242 chars),
   proving the mode actually turned off, not just that a new trip was
   generated.
5. Adversarial: `"be my tour guide through a new 3-day Rome itinerary"`
   (fresh conversation) → classified as a planning turn (itinerary
   generated, 9 items), `tour_guide_mode` correctly stayed `False`.

## Open items / follow-ups

- No UI indicator for the mode, per explicit product decision this
  session — it's a silent backend behavior change. Could be added later
  (the existing `banner`/`banner--*` CSS pattern in `TripView.tsx` would be
  the natural fit) if users want visibility into whether it's active.
- The classifier's existing fail-open-to-`"new_trip"` behavior on any
  error will also silently turn tour-guide mode off during an active
  session — accepted as-is per explicit user confirmation, not
  special-cased.
